# Alpha — Repository Audit & Implementation Roadmap

**Date:** 2026-08-16
**Status:** Baseline audit (read-only). No code was modified during the audit.
**Scope:** Full monorepo audit per the Alpha personal-finance system spec: backend, database, frontend, CLI, Telegram, n8n, tests, docs, security.

---

## 1. Executive Summary

Alpha is a mature monorepo with substantial working functionality, not a greenfield:

- **Backend:** FastAPI microservice (`apps/api/main.py`, port 8444) with ~25 routers in `packages/api/backend/routers/`.
- **Frontend:** Canonical Next.js 16 app (`apps/web/`, **broken API wiring**) + frozen legacy Vite app (`packages/web/`, deprecated 2026-08-11).
- **CLI/TUI:** Python Rich app (`apps/cli/`) with expense/income/investment trackers, OCR receipt reader, behavioral finance, stock ML, genetic optimizer.
- **Database:** PostgreSQL canonical (per-profile schemas) + SQLite for local-only stores (audit, cache, legacy import).
- **Automation:** n8n (3 workflows tracked; 2 broken), APScheduler background jobs, Celery config.
- **Tests:** 255 pytest functions across unit/integration/regression/stability/automation/audit suites. CI runs only the unit suite.

The system already implements: expenses, income, budgets, goals, recurring detection, cashflow forecast (basic), behavioral finance, investment FIFO tracking, net worth snapshots, OCR receipt reader, Telegram text + receipt flows, multi-profile isolation.

The system is **missing**: unified transaction ledger, real multi-account support, double-entry transfers, safe-to-spend, anomaly detection, weekly reports, budget thresholds/alerts, recurring payment reminders, NL intent-based queries, robust confirmation idempotency, and a coherent frontend.

## 3. Architecture as Found

### 3.1 Topology

```
Telegram (n8n webhook / getUpdates poll) ──▶ FastAPI :8444 ──▶ PostgreSQL (per-profile schemas)
                                                        └──▶ SQLite (audit, cache, legacy)
Next.js apps/web (canonical)  ──▶ FastAPI REST
Vite packages/web (legacy/frozen)
CLI apps/cli (Rich TUI) ──▶ local SQLite + PG via Database bridge
n8n (currency/price/telegram workflows) ──▶ REST / PostgreSQL
APScheduler background jobs (networth, price refresh, behavioral report, recurring detect)
```

- **Router registration:** `apps/api/main.py:374-400` dynamically imports routers from `packages.api.backend.routers.*` (+ `packages.api.telegram_bot`).
- **Auth:** Bearer API key + scope system (`require_scope`), rate limiting in `audit_middleware`, SQLite audit log. Dev-mode bypass via `FINANCE_TRACKER_DEV_MODE=1`. User sessions (register/login) in SQLite `audit_log.db`, PBKDF2 100k iterations, 12h expiry.
- **DB bridge:** `DatabaseManager` (psycopg2 pool, `search_path` = active profile + shared schemas). `SchemaInitializer` creates per-profile schemas at startup from `005_profile_schema_template.sql` (18 tables). Prisma rewrites `DATABASE_URL` schema to active profile.
- **Multi-tenancy:** per-profile Postgres schemas (`user_zhvn`, `personal`, `business`, …); `system.profiles` holds profile registry.

### 3.2 Per-Profile Schema (18 tables)

`expenses, incomes, investments, sell_transactions, historical_prices, recurrence_candidates, user_stats, fx_rates, manual_balances, cash_split, transfer_log, behavioral_snapshots, networth_snapshots, budgets, goals, stock_favorites, virtual_accounts, reward_state`

No `transactions`, `accounts`, `merchants`, `categories`, or `transfers` (double-entry) tables exist.

### 3.4 Telegram Integration (existing)

- **Text flow:** `telegram_handler.py` — commands `/summary`, `/daily`, `budget`, `saldo/rekening`, plus regex add patterns (`tambah pengeluaran 50k makan`, `/expense 35k kopi`). Amount parser handles `50k`, `1.5jt`, `Rp 75.000`. Category keyword detection.
- **Receipt flow:** `telegram_bot.py` — webhook → n8n posts scanned receipts to `/telegram/receipt_pending` → inline-keyboard confirmation (edit merchant/total/date/category/payment, save/cancel, bulk queue) → writes to SQLite + Postgres. **State held in an in-memory dict (`PENDING_RECEIPTS`)** — no expiry, no user auth, no replay/idempotency protection, lost on restart.
- **Polling:** `telegram_poll.py` standalone getUpdates poller (opt-in `ENABLE_TELEGRAM_POLL=1`).
- **Auth gap:** `/telegram/*` routes require `write` scope (API key), but n8n→Telegram webhook validation relies on `X-Telegram-Bot-Api-Secret-Token`; no per-chat user authorization for financial actions.

### 3.5 Frontend (apps/web)

- Next.js 16.2.6, React 19, Tailwind 4, recharts, framer-motion. Pages: `/` (dashboard), `/analytics`, `/business`, `/logs`, `/behavioral` + `/reward` (stubs).
- **Contract mismatches (blocking):** `page.tsx` calls `/expenses` (catch-all returns HTML 200), defaults port 8000 (API is 8444), `analytics/page.tsx` expects `expData.expenses` arrays but backend returns `{items}`, `/api/behavioral/report` does not exist, CORS excludes Next dev origin `:3000`, client sends Bearer but not HMAC signature for writes.

### 3.6 n8n

- `n8n_telegram_workflow.json` — Telegram trigger → download photo → `POST :8444/api/receipt/scan` (placeholder host).
- `n8n_currency_monitor_workflow.json`, `n8n_automation_price_monitor_workflow.json` — **column mismatches vs `002` migration** (insert `symbol/price/timestamp` / `currency/timestamp`; table has `asset_symbol/current_price/recorded_at` / `base_currency/fetched_at`).
- No finance workflows (budget alerts, recurring reminders, goal monitoring, reports, anomaly) exist.
- `conductor/n8n/` gitignored; workflow JSONs duplicated and untracked.

## 6. Implementation Roadmap

Order is risk-first. Reuse existing engines (OCR, behavioral, investments, recurring) rather than rebuilding.

### Sprint 0 — Stabilize
1. Fix goal PATCH bug + regression test.
2. Fix `apps/web` API wiring (prefix, ports, CORS, `/api/behavioral` contract, write signature).
3. Rotate/scrub committed secrets; enforce non-default `SECRET_KEY`/DB creds in all configs.
4. Fix n8n INSERT column mismatches.
5. Wire `_verify_hmac`; fix read-scope POSTs in `ai.py`.
6. Track `migrations/` in git; add migration for `market.ohlcv_cache`/`latest_prices`; reconcile `recurrence_candidates`.

### Phase 2 — Transaction & Account Model
- Migration `008` (007 was consumed by Sprint 0): `transactions` (unified, with type/source/confidence/idempotency_key), `accounts` (type enum, bank/e-wallet/cash/investment), `merchants`, `categories`; double-entry `transfer_pairs`; relax duplicate-blocking unique constraints (legacy `expenses`/`incomes` UNIQUEs dropped; dedup now via `transactions.idempotency_key`).
- Transaction/Account/Merchant/Category engines (`packages/api/backend/finance/ledger_engine.py`) + API (`routers/ledger.py`); backfill from existing expenses/incomes where safe (`expense:<id>`/`income:<id>` keys, dry-run support, rerunnable).
- Unit + integration tests (`tests/unit/test_ledger_engine.py`): zero-amount, negatives, huge amounts (MAX_AMOUNT boundary), same-day, month/year/leap boundaries, empty sets, missing category/account, duplicate/idempotency replay, transfer neutrality, backfill idempotency, API route-order + error mapping.

### Phase 3 — Telegram NL Input + Confirmation

### Phase 4 — Receipt → Telegram
- Reuse OCR ensemble; harden confirmation; low-confidence → mandatory confirmation.

**Status: IMPLEMENTED — committed `23116df` (Phase 4 files only).**
- Confidence policy (user decision): ALL receipts require manual confirmation; OCR confidence is shown in the confirmation message (`Kepercayaan OCR: N%`), with a `⚠️ Akurasi rendah` warning when below `RECEIPT_LOW_CONFIDENCE` (default 0.80, env-tunable). No auto-commit.
- Hardening: `confirmation_engine.validate_draft_fields()` (amount > 0 / ≤ 1M / parseable, merchant non-empty) rejects garbage receipts up-front — no silent ledger failures downstream. `receipt_pending` (n8n path) and `telegram_poll.py` photo path validate before queueing; mixed batches keep valid items and report rejected ones.
- Tests: 4 unit tests for `validate_draft_fields` (29 engine tests total); 4 bot tests (low-confidence warning, high-confidence still confirms, invalid rejected, partially-invalid batch). Regression: 470 passed; 4 pre-existing `test_session4_integration.py` auth-401 failures unchanged.
- n8n flow unchanged (`/api/receipt/scan` → `/telegram/receipt_pending`); `confidence` already flows through to the store.
- Committed `23116df` on request (Phase 4 files only).

### Phase 7 — Recurring Detection + Reminders
- Confidence scoring + verification; n8n WF-09 (detection) and WF-10 (daily reminders, dedup).

**Status: IMPLEMENTED (worktree, uncommitted).**
- `recurring_service.py` — canonical-ledger recurring engine (`transactions`, expense+income, transfers excluded): group by type/category/merchant/normalised description (trailing noise stripped); cadence = monthly (day-of-month, 3-day interval tolerance) or weekly (same weekday); confidence = regularity 45% + occurrence count 35% + amount stability 20% (min 0.35); candidates persisted idempotently keyed by SHA-256 (WF-09 re-runs never duplicate); `next_due` surfaced in results.
- Verification gate: `verify_candidate()` flips `is_confirmed`; only confirmed templates generate reminders.
- Reminders (WF-10): `generate_reminders()` recomputes the next due date from the template cadence, fires within [as_of − 3, as_of + 2] days, skips periods already covered by a matching transaction (amount ±25%), and dedups via `recurring_reminders` UNIQUE(candidate_id, period_key) — period_key = `YYYY-MM` (monthly) or ISO week `YYYY-Www` (weekly); `mark_reminder_sent()` flips status pending → sent.

- Tests: 18 unit (`tests/unit/test_recurring_service.py`: monthly/weekly cadence, income detection, transfer exclusion, idempotent upsert, verification gate, due-window, period-coverage skip, period-key dedup + next-month, weekly period keys, mark-sent, errors).
